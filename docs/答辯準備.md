# AgentAQI 期末答辯準備

> 給口試/答辯用的整理:動機、使用情境、程式講解、導師可能問的問題與標準答案。

---

## 零、30 秒電梯版(What / How / Why)

- **What**:一個「個人 agent 空氣品質監控平台」—— 把全台 20 縣市的**真實**空品資料,收斂成「**你這個人**現在能不能出門」的健康決策,並能讓聊天 bot 把答案帶進 Discord。
- **How**:五個公開 API(EPA 即時+歷史 / CAMS / Open-Meteo / 民生公共物聯網 / LASS)→ 三代理人 pipeline(A 純 ETL → B LLM 風險分析 → C LLM 個人化建議,注入你的 ICD-10 / BMI / 閾值 + RAG 文獻)→ SQLite 時序庫 + 10 個 SECTION 視覺化 → 匯出一份 JSON,任何 bot 來讀就能回答。
- **Why 前端**:bot 只是「最後一哩的傳遞」;**建檔(表單/上傳)、視覺分析(熱力圖/時間軸)、驗證閉環(打卡算相關)都只能發生在前端**。一次 pipeline 計算,bot 端 N 次免費回答。

---

## 一、為什麼做這個專案(動機)

**一句話定位:把「給所有人看的全台空品監控」升級成「給你這個人的健康決策」。**

環境部 EPA 已公布每個縣市的 AQI,但「台中 AQI 95」這個數字,對一個**有過敏性鼻炎的 19 歲學生**或**72 歲 COPD 的阿公**來說,沒有回答他真正想問的:「**我現在到底能不能出門?要不要戴口罩?**」官方數字是給「全民」的平均,不是給「你」的決策。

核心論點:**全民監控 → 個人健康決策**,用三層價值串起來:

1. **多源真實資料** —— 同時打五個公開 API(環境部 EPA 即時 `aqx_p_432` + 歷史 `aqx_p_488`、Copernicus CAMS 模式、Open-Meteo 氣象、民生公共物聯網約 1 萬個政府微型感測器、LASS-net 社群 Airbox),互補死角。
2. **收斂成「對你一個人」的答案** —— 用年齡 / BMI / ICD-10 診斷碼 / 病歷 / **你自己設的 AQI 閾值**,加上 RAG 文獻(WHO 2021 / EPA NAAQS / Lancet 2023),算「今天還能在戶外幾小時、要哪種防護」。
3. **用你的日誌驗證敏感度(閉環)** —— 每天打卡症狀,系統跟當天真實 AQI 算**皮爾森相關 r**,用你自己的數據證明空污對你個人有沒有影響。

> 開場白:「前 7 個 SECTION 是全台監控,**SECTION 08 開始是整個專案的轉折點** —— 從『所有人』切換到『你這個人』。」

## 二、使用情境

- **72 歲、COPD、住台北的阿公(demo persona)**:封面填檔 → 跑 Pipeline → 主畫面跳「⚠ 台北 AQI 超過你設的閾值 50」紅色橫幅;SECTION 08 算出安全戶外時數 + 建議 N95;SECTION 07 預警員給「您 72 歲且有 COPD,今天 PM2.5 偏高…」針對性建議。
- **19 歲、過敏性鼻炎的學生**:「過敏性鼻炎」不在傳統「五大敏感族群」裡 —— 正是專案**刻意不用粗分類**的原因。勾 ICD-10 J30、上傳病歷 PDF(進 RAG、1.4× 加權),建議貼著本人。
- **想長期追蹤的一般使用者**:每天在 SECTION 09 打卡,兩週後散點圖出現「症狀 vs AQI」正相關 r,第一次用自己的數據證明自己對空污敏感。
- **不想一直開網頁的人**:在 Discord 打 `@bot 台中現在空氣如何`,bot 讀 JSON 回最新數據 + persona 提醒,不用自己查、不用 API key。

## 三、架構速覽

```
五個真實 API ──► 採集者 A(純 ETL,無 LLM,並行清洗)
                     │ snapshot / 24h 歷史 / 民間感測
                     ▼
              分析師 B(LLM)── 加權風險公式 + RAG 文獻 → 3 段風險報告
                     ▼
              預警員 C(LLM)── 依 persona + RAG 個人病歷 → 逐城市個人化建議
                     ▼
   SQLite 時序庫(7 天趨勢 / 週對比 / 健康日誌) + 匯出 latest_aqi.json
                     ▼
              Agent Bot「來這裡讀」JSON → 在聊天平台回答
```

重點:**只有 B、C 用 LLM,A 是純 Python**。AQI、風險分數、排名全部 pandas 算好,LLM 只負責「解讀 + 給建議」,不負責產生數字。

## 四、程式講解(三段最具代表性的)

### (1) 個人化核心 —— `safe_hours` 公式(SECTION 08)

```python
excess     = max(0.0, current_aqi - _thr)          # _thr = 你自己設的 AQI 閾值
safe_hours = max(0.0, 12.0 - excess * 0.15)
if   excess <= 0:  建議 = "✓ 可正常戶外活動"
elif excess <= 30: 建議 = "🧣 一般口罩,避免長時間激烈運動"
elif excess <= 60: 建議 = "😷 N95/KF94,單次戶外不超過 1 小時"
else:              建議 = "🚫 強烈建議留在室內"
```

刻意做成**透明、可解釋**的公式,門檻 `_thr` 是你自己設的 —— 閾值越低(越敏感)→ 安全時數越短。**刻意不**塞「BMI>30 就減 5 分」這種沒文獻根據的魔術數字,更細的年齡 / 疾病交給下方 LLM 文字建議。被問「憑什麼」時站得住腳。

### (2) 個人化的「零回歸」設計 —— 一個會說話的空字串

```python
age   = st.session_state.get("user_age", 0) or 0
diags = st.session_state.get("user_diagnoses", []) or []
hist  = (st.session_state.get("user_med_history") or "").strip()
if not (age or diags or hist):
    return ""        # 沒填任何東西 → 回空字串 → prompt 完全不變 → 行為跟「沒個人化」一模一樣
```

這個空字串是 load-bearing 的:保證個人化是**疊加、零回歸**的,沒填的人 prompt 跟加功能前逐字相同。(`user_age` 預設刻意是 `0` 不是 `30` —— 因為 `30` 是 truthy,會讓這判斷誤判「有填」而永遠把 30 歲注入 LLM,這是真的被抓到修掉的誠實性 bug。)

### (3) RAG 其實只有 8 行 —— 字元 bigram + 個人病歷加權

```python
qgrams = {q[i:i+2] for i in range(len(q)-1)}              # 問題切成「相鄰兩字」集合
hits   = sum(1 for i in range(len(c)-1) if c[i:i+2] in qgrams)
score  = hits / (len(c) ** 0.5)                           # ÷√長度 → 長短文件公平
if chunk["scope"] == "personal":                          # 你上傳的病歷
    score *= 1.4                                          # 加權,讓短病歷排得贏長篇通用文獻
```

**刻意不用 vector DB / embedding** 的取捨:對「空品健康」這個只有 4 份種子文獻 + 幾份上傳 PDF 的小領域,字元重疊零依賴、即時、可解釋,程式也誠實註明「缺點是無法處理同義詞」。`√長度` 避免短 chunk 永遠贏;`1.4×` 修正個人病歷字少被擠掉的長度偏誤。

## 五、導師可能問的問題 + 標準答案

### 🎯 為什麼還要做 Streamlit 前端,不讓龍蝦(OpenClaw)/ Hermes bot 自己跑就好?

**先澄清前提**(導師若有誤解要先扶正):三代理人**從來不是跑在龍蝦裡** —— 它們是 App 內直接呼叫 LLM HTTP API 的三個階段。龍蝦 / Hermes 在本專案只扮演「聊天平台的傳遞端」。所以這題真正在問的是:「為什麼不把整個產品做成一隻 bot?」四個理由:

1. **工作性質不同 —— 這個產品的核心互動聊天介面做不好。** 建檔需要**結構化輸入**(ICD-10 多選、身高體重、PDF 病歷上傳),表單一頁搞定、聊天要來回十幾句;分析需要**可互動視覺化**(20 城市 × 24h 熱力圖、時間軸 scrubber、雷達圖、地圖、回歸散點),聊天室貼不出來;驗證需要**長期閉環**(每天打卡 → 皮爾森 r),需要持久 UI。
2. **成本與延遲的攤提 —— 一次計算、多次消費。** 若 bot 每被問一次就自己抓 EPA + 跑 LLM:每問都要等、都燒配額,經 gateway 還多 30–60 秒冷啟。現在的設計:Pipeline 跑一次(直連 LLM、毫秒級開銷),結果落地成 JSON;bot 之後回答 N 次都**即時、零成本、不需要任何 API key**。
3. **解耦的遷移實證 —— 本專案親身證明過。** 對接端從 OpenClaw 換成 Hermes 時,因為契約只是一份 `latest_aqi.json`,**遷移成本趨近於零**(換一個會讀檔的 bot 而已)。如果整個產品寫死在龍蝦裡,換框架等於重寫 —— 這正是專案從 LobsterAQI 改名 AgentAQI 的原因:不綁特定產品。
4. **信任與誠實需要 UI。** data_mode 徽章(real/mock/demo)、資料新鮮度燈號、官方 vs 民間感測器對比、清洗報告(原始 X 筆 → 保留 Y 筆)—— 這些「為什麼你該信這個數字」的證據需要儀表板呈現;聊天泡泡丟一個數字,使用者無從查證。

**反問句**:「如果只有 bot,使用者要在哪裡填 ICD-10、上傳病歷、看熱力圖、拖時間軸、打卡算相關係數?」

**一句總結**:龍蝦/bot 是「**最後一哩**」,Streamlit 是「**工廠 + 展示間**」—— bot 負責把算好的答案送到使用者在的地方;前端負責把答案**算出來、證明它可信、並讓使用者建立與驗證自己的健康檔案**。

### 架構 / 定位

- **為什麼拉取不推送?** 推送要架 endpoint、註冊排程、處理失敗重試;拉取只要一份本機 JSON。更重要是**解耦** —— App 和 bot 只共用 JSON 契約,換 LINE/Slack/任何框架都只要會讀這份檔(所以產品名都改成通用「Agent Bot」)。語意也更誠實:不主動推,是「你問,bot 才來讀」。
- **這只是 dashboard 嗎?有真工程嗎?** 圖表之外:自動 schema migration 的 SQLite 時序層、雙來源 UPSERT、能在真實 Pipeline 重跑時不被覆蓋的 demo 隔離(真的 PK 碰撞 bug 修出來的);字元 n-gram RAG;多家 LLM 抽象層(timeout 調校 + 截斷偵測);解耦 JSON 契約。CHANGELOG 約 600 行記了多個 root-cause 分析(age=30 truthy、created_at 覆寫、demo 撞庫)。
- **跟直接看 EPA 網站差在哪?** EPA 給「城市」一個數字,不會告訴「你」要不要出門。AgentAQI 把 20 城市收斂成對你一個人的答案,再用 RAG 接文獻、用打卡的皮爾森相關證明你個人的敏感度。是「全民監控 → 個人健康決策」。

### Agent / RAG

- **這真的是 multi-agent,還是依序呼叫函式?** **誠實說:是 `run_pipeline()` 裡循序、可控的函式編排,不是自主 agent。**「三代理人」是三個分工明確的階段(A→B→C),透過 `st.session_state` 傳資料。定位成「**角色分明、確定性、可解釋的 pipeline,其中兩段由 LLM 驅動**」。而且專案就因為「不該為 multi-agent 而 multi-agent」砍掉兩個沒用的 agent —— 反而是成熟度。
- **為什麼從 5 砍到 3?** 原本 5 個裡有 3 個的 LLM 呼叫只是「對剛跑完的 Python 寫一句評論」,沒進下游;Critic 打的 0–100 分沒觸發任何重試。重構把 ETL 集中成純 Python 採集者,LLM 只留在「分析」和「個人化建議」。
- **這是真 RAG 嗎?為什麼不用向量庫?** 是檢索增強,用字元 bigram 不是 embedding。刻意取捨:embedding 要裝 sentence-transformers(數百 MB)+ 向量庫,對 4 份種子文獻的小領域過度設計。字元重疊零依賴、即時、可解釋,且 `retrieve_rag_chunks` 是唯一檢索接縫,要換很容易。
- **怎麼確定 LLM 沒亂編數字?** 四層:① 反幻覺 prompt 明文禁止編造、查無要回「目前資料中沒有這項資訊」;② **每個數字 Python 先算好再塞進 prompt**,LLM 只轉述不計算;③ RAG 限定「只能引用以下條目」+ 非空 fallback;④ 截斷誠實標示。數字本身是確定性的,不是 LLM 生的。

### 技術選型

- **為什麼 SQLite 不用 InfluxDB/Timescale?** 規模問題:20 城市 × ~10 欄 × 每小時 ≈ 5,000 列/天,一年 ≈ 17.5 萬列 ≈ 幾 MB。專用時序庫過度設計。SQLite 是標準庫內建單檔零安裝,對校園 demo / 個人工具最合適,也扛得住視窗 AVG/MAX 與 JOIN。(理由寫在 tsdb.py 模組註解。)
- **為什麼直接打 LLM HTTP 不用 gateway?** 延遲。gateway/plugin 每次多 30–60 秒冷啟,對「按下去幾秒看到結果」太慢。直接 HTTP 毫秒級;代價用一張 `LLM_PROVIDERS` 設定表 + 共用 OpenAI 格式路徑補回,加一家只要一筆 dict。

### 資料 / 誠實 / 隱私

- **資料是真的還是模擬?** 預設真的(四個活來源)。合成只是 EPA 失敗的 fallback,一旦使用 UI 顯示「MOCK 模擬資料」、`data_mode='mock'`,絕不假裝成真。demo 歷史另標 `demo`、可一鍵清除,簡報也會誠實說明。
- **即時與歷史來自不同系統,會兜不起來嗎?** 會,有修。即時是 EPA 測站、歷史常是 CAMS(偏高 20–50%)。`_anchor_history_to_snapshot` 把每城歷史按「即時/歷史」比例重縮放(clamp 0.3–3.0,只動 AQI/PM2.5/PM10),保留趨勢形狀、對齊「現在」 —— 拖時間軸往回不會出現假尖峰。
- **收集健康資料,隱私怎麼辦?** 個人檔案只存本機 session,只送你自己設定的 LLM 金鑰、寫進本機 JSON 給你自架的 bot 讀,**不傳給作者或任何第三方** —— 這段說明永遠顯示在填寫表單上方。
